## 骰子类型与投掷

- **7 种元素骰**（每种游戏元素对应一种）+ **1 种万能骰**
  = 共 8 种类型
- 每次 `on_round_start` 时投掷 **8 枚骰子**
- 每枚骰子独立地以 **1/8 的概率**落在 8 种类型中的任意一种（均匀分布）
- 期望每次约获得 1 枚万能骰
- **未使用的骰子在回合结束时丢弃**。回合之间不结转。
- 骰子池以计数器组 `Tag.Dice` 存储，按玩家按类型分配
  （8 种类型 × 2 名玩家 = **共 16 个计数器**）

回合结束时丢弃的规则使骰子管理成为**每回合的资源决策问题**，
而非多回合的积累博弈。每个回合都是一个独立的、以随机初始资源开始的规划问题。

## 费用原子

每张卡牌或技能的费用由恰好三种原子组合而成：

### 原子 1：`n 同色`

玩家在**支付时**选择一种颜色，并支付该颜色的 `n` 枚骰子。
玩家无需提前承诺特定颜色——在打出卡牌的瞬间才选择支付哪种颜色。

**支付规则**：
- 可用 ≥n 枚任意单一非万能骰满足（例如 3 火）
- 万能骰可替代所选颜色（例如 2 火 + 1 万能满足"3 同色（火）"）
- **纯万能支付合法**：`n` 枚万能骰满足 `n 同色`——
  它们全部视为同一隐含颜色（与原神 TCG 规则一致）

### 原子 2：`n 无色`

`n` 枚任意颜色的骰子。玩家自行决定从池中花费哪 n 枚。无颜色限制。

**支付规则**：
- 池中任意 n 枚骰子的多重集均合法
- 合法行动枚举时，等价的多重集支付会去重：
  `{冰, 冰, 火}` 和 `{火, 冰, 冰}` 是同一种支付方式（骰子顺序无意义）

### 原子 3：`n X 色`

`n` 枚特定元素 X 的骰子（例如火技能需要"3 火"）。
颜色由卡牌/技能声明时固定，不由玩家选择。

**支付规则**：
- 可用 ≥n 枚颜色 X 的骰子满足
- 万能骰可替代其中任意数量（例如"3 火"可用 2 火 + 1 万能，
  或 1 火 + 2 万能，或 3 万能支付）

## 费用结构

实践中只出现以下三种组合结构。其他组合**不在费用语法支持范围内**。

### 结构 1：纯同色 — `n 同色`

```
cost = SameColor(n=3)
```

示例：需要"3 同色骰"的技能（颜色灵活）。

### 结构 2：纯无色 — `n 无色`

```
cost = Void(n=2)
```

示例：费用为 2 枚任意颜色骰子的卡牌（如中性工具卡）。

### 结构 3：特定色 + 无色 — `a X 色 + b 无色`

```
cost = Specific(element=FIRE, count=2) + Void(count=1)
```

示例：费用为"2 火 + 1 无色"的火技能（原神 TCG 中常见模式）。

### 不支持的结构

- **混合特定色**：例如"1 火 + 1 冰 + 1 无色"。语法不允许一个费用中出现多种特定色要求。
- **多个同色**：例如"3 同色 + 2 同色"。每个费用中最多使用一个同色原子（如有）。
- **特定色 + 同色**：例如"2 火 + 3 同色"。同样不支持。

## 支付枚举（合法行动列举用）

对于每种费用结构，引擎枚举所有不同的支付多重集：

### 纯特定色（`n X 色`）

根据万能骰替代数量（0 枚万能、1 枚万能……n 枚万能）最多有 `n+1` 种选项，
受支付能力剪枝。

典型值：1-3 种选项。

### 纯同色（`n 同色`）

对 7 种非万能颜色 X 各自枚举 `n+1` 种万能替代级别
（0 万能 + n X，1 万能 + (n-1) X，……，n 万能 + 0 X），
受支付能力剪枝。此外，纯万能支付算作一种
（统一归并至某个"颜色"——惯例取第一个出现的颜色）。

典型值：3-10 种选项。

### 纯无色（`n 无色`）

组合枚举：当前池中可取的所有 n 枚骰子的多重集。
上界为 `C(池中不同颜色数 + 万能, n)`。

典型骰子池约有 ~5 种非零类型，故 n=2 → 最多 ~15 种，
n=3 → 最多 ~35 种。**这是行动空间增长的主要来源。**

### 特定色 + 无色（`a X + b 无色`）

以下两部分的乘积：
- 特定色部分的支付选项（如上所述枚举 `a X 色`）
- 无色部分的剩余池支付选项（在减去特定色支付后，枚举 `b 无色`）

典型值：5-30 种选项。

## 切换费用

切换出战角色花费 **1 无色**（1 枚任意颜色骰子，可用万能骰替代）。

**无每回合切换次数限制**。只要能支付每次切换的无色费用，
玩家可在一个回合中进行任意次切换。

这使得在回合中途换人以重新绑定调和目标或出战角色敏感效果的连击成为可能
（详见 `decisions.md` D12 中的两个典型案例）。

## 调和费用

调和消耗调和玩家手中的 **1 张手牌**，并将 **1 枚非当前元素的非万能骰**
转换为当前出战角色的元素。

**费用**：**0 枚骰子**。调和只丢弃卡牌，不额外消耗骰子。

**每回合使用上限**：隐性受限于
`min(手牌数, 非匹配非万能骰数量)`。典型上限为每回合 5-6 次。
实际使用量为 0-2 次（每次调和都要烧掉一张卡，而卡牌本身是宝贵资源）。

**上下文敏感性（关键）**："当前元素"是在**调和执行时刻**读取的，
而非行动提交时。若玩家在排队和执行之间切换了角色，
调和将以新出战角色的元素为目标。这种路径依赖性正是 MCTS
无法抽象调和选择的原因（见 D12）。

## 零骰费用行动

**初始状态下，没有任何技能具有内在的零骰费用。** 每个技能和卡牌
至少需要一枚骰子。

**但是**，增益效果可以将卡牌/技能的费用降至零（例如"本回合下一个技能费用为 0"的增益）。
引擎通过现有的费用修改钩子路径处理此情况——DSL 中声明的费用为基础费用，
增益在 `on_action_check` 或类似钩子中对其进行修改。

调和是特殊情况：它本身具有 0 骰费用（消耗 0 骰、丢弃 1 张手牌）。

## 隐藏信息

骰子的引入在对手手牌内容和对手牌堆组成之外，
为隐藏信息集新增了**第三个维度**。

**对手骰子状态**：
- 总数量为**公开信息**（双方都能看到"对手有 N 枚骰子"）
- 各类型的具体分布对对手而言是**私有信息**

确定化采样器（见 `determinization.md`）必须从与已知总数量及各类型 1/8
投掷分布相符的多项分布中采样一个 8 维向量（每种骰子类型的数量），
同时根据对手本回合已公开的历史支付记录进行调整。

## 骰子作为计数器组

与现有计数器 + 钩子系统的集成：
- 每种骰子类型作为 `Tag.Dice` 下的一个计数器
- 计数器为 `PerPlayer` 作用域，故 8 个计数器 × 2 名玩家 = 16 个
- `on_round_start` 钩子（在 DSL 中）重新投掷全部 16 个计数器
- `on_card_play` / `on_skill_use` 钩子根据支付结构扣除对应计数器
- 费用可支付性检查是一个新的引擎辅助函数，读取这些计数器

## 公开支付中的对手信息披露

一个关键推断来源：当对手打出行动时，其支付的骰子是可观测的
（费用结构为公开信息）。这会**泄露其骰子池信息**：

- 若对手使用了"3 火"技能，则可知对方当时至少有 3 枚（火 + 万能）骰
- 支付后，对方剩余骰子总数减少 3

确定化采样器可利用此信息对对手骰子生成更精确的后验估计，
但 MVP 阶段采用朴素的对剩余多项分布均匀采样。

- 切换费用 + 无限切换连接：0.5 天

- 通过钩子驱动的增益费用减少：0.5 天
- 观察布局（+16 个计数器槽位）：0.5 天

**这超出了 MVP 范围**。推迟至 MVP 训练经验证并稳定后再实施。

## MVP 前向兼容性约定

MVP 代码不得做出任何在骰子机制到来时会被破坏的假设：
1. `get_action_refs` 返回 `(kind, skill_ref, card_ref)` 三元组——
   骰子到来后，会附加一个 8 维骰子组合向量作为第四个字段
2. MVP 中 `MAX_ACTIONS = 64`——必须可配置地增长至 128 或 256，
   无需重构策略头
3. 观察维度已通过引擎查询方式获取（见 `network_design.md` 前向兼容约束），
   因此新增 16 个骰子计数器只是配置变更而非重构
4. 行动特征计算（`hook_emb + target_proj`）必须为 `dice_combo_proj` 残差加法留有空间
5. MVP 引擎中不含费用可支付性检查，但所用模式
   （引擎侧 `GetLegalActions` 枚举可负担的组合）与骰子枚举的形式相同

# 游戏规则与开发规则

本文档定义了 GICG Sim 项目中的游戏规则和开发规范。

## 游戏规则

### 游戏基础

#### 玩家与区域

- 游戏支持 **2 名玩家**对战
- 每个玩家拥有以下区域：
  - **手牌区**：上限 16 张
  - **支援区**：上限 4 张
  - **角色区**：最少 1 个，玩家上限 3 个，NPC 可更多（上限 6 个）
  - **后备角色区**：当角色区全部被击败时，从后备角色区补充
  - **召唤物区**：上限 4 个
  - **骰子区**：上限 12 个

#### 角色属性

- **生命值（HP）**：角色最大生命值，当前生命值降至 0 时角色被击败
- **能量（Energy）**：角色能量上限，用于释放元素爆发
- **元素类型**：角色的元素属性（火、水、风、雷、草、冰、岩）
- **技能**：每个角色拥有普通攻击、元素战技、元素爆发三种技能

#### 骰子系统

**骰子类型**：
- 元素骰子：火、水、风、雷、草、冰、岩
- 万能骰子（Omni）：可以当作任意元素使用

**骰子消耗规则**：
1. 技能费用由以下部分组成：
   - 特定元素骰子数量
   - 匹配元素骰子数量（当前角色元素）
   - 任意元素骰子数量
   - 能量需求（元素爆发）
2. 万能骰子可以替代任何元素骰子
3. 费用检查按优先级：特定元素 → 匹配元素 → 任意元素

**元素调和**：
- 弃掉一张手牌
- 将一个任意骰子转换为当前角色元素骰子

#### 技能系统

**技能类型**：
- **普通攻击（Normal Attack）**：基础攻击技能
- **元素战技（Elemental Skill）**：元素技能
- **元素爆发（Elemental Burst）**：需要能量的强力技能

**技能属性**：
- 伤害元素类型（物理、各元素、穿透）
- 伤害数值
- 费用需求（骰子 + 能量）
- **特殊效果**：技能可以附加多种特殊效果（见下方）

**技能特殊效果**：

技能可以附加多种特殊效果，包括但不限于：

1. **计数效果**：
   - 记录技能使用次数
   - 根据使用次数触发不同效果
   - 示例："第三次使用该技能时威力 +2"

2. **元素附着效果**：
   - 对目标或自己附着元素
   - 用于触发元素反应
   - 示例："使用后对敌人附着水元素"

3. **伤害修改效果**：
   - 修改伤害数值或类型
   - 支持加值、乘值、替换等
   - 示例："如果敌人有火元素附着，伤害 +1"

4. **状态添加效果**：
   - 为目标添加状态（Buff/Debuff）
   - 示例："对敌人添加 2 回合的冻结状态"

5. **条件效果**：
   - 根据条件触发效果
   - 示例："如果自己生命值低于 50%，伤害 +2"

6. **费用修改效果**：
   - 修改技能的费用需求
   - 示例："如果手牌数 ≥ 5，费用 -1"

7. **触发效果**：
   - 在特定事件时触发
   - 示例："受到攻击时，对攻击者造成 1 点伤害"
   - 包含完整的上下文信息（伤害来源、目标等）

**目标与动作系统**：

技能通过目标与动作系统定义行为，支持：
- **多种目标类型**：站场角色、下一个角色、所有角色、自己等
- **多种动作类型**：伤害、治疗、元素附着、状态添加等
- **动作组合**：一个技能可以执行多个动作
- **连锁动作**：攻击下一个角色、治疗下一个角色等
- **群体动作**：群体伤害、群体治疗等

详细的技能效果系统设计请参考：
- [技能效果系统设计文档](skill_effects_design.md)
- [目标与动作系统设计文档](target_action_system.md)

#### 伤害系统

**伤害类型**：
- **物理伤害**：无元素属性的伤害
- **元素伤害**：火、水、风、雷、草、冰、岩
- **穿透伤害**：无视护盾的伤害

**元素反应**：

1. **增幅反应**（直接增加当次伤害）：
   - 蒸发（水+火）：伤害 × 2
   - 融化（火+冰 或 冰+火）：伤害 × 2

2. **剧变反应**（追加一次伤害）：
   - 超载（火+雷）：造成 2 点火元素伤害
   - 感电（水+雷）：造成 1 点雷元素伤害（对双方所有角色）
   - 超导（冰+雷）：造成 1 点冰元素伤害
   - 扩散（风+其他元素）：造成 1 点对应元素伤害（对相邻角色）
   - 燃烧（火+草）：造成 1 点火元素伤害（持续回合）
   - 绽放（水+草）：生成草原核，造成 2 点草元素伤害
   - 激化（雷+草）：生成激化领域，下次雷/草伤害 +1

**伤害计算流程**：
1. 基础伤害计算
2. 元素反应判定（增幅反应修改伤害，剧变反应追加伤害）
3. 伤害队列处理（允许修改未结算的伤害）
4. 伤害结算

#### 回合流程

1. **开局阶段**：
   - 选择角色
   - 初始手牌（5 张）
   - 初始骰子（5 个）

2. **投掷阶段**：
   - 投掷 8 个骰子
   - 可以选择重投一次

3. **行动阶段**：
   - 玩家可以执行以下行动：
     - 使用技能
     - 切换角色
     - 使用卡牌
     - 元素调和
     - 宣布结束回合
   - 双方轮流行动，直到双方都宣布结束回合

4. **结束阶段**：
   - 召唤物效果触发
   - 状态效果结算
   - 回合切换

#### 胜利条件

- 击败对手所有角色（包括后备角色）

## 开发规则

### 代码规范

#### 命名规范

- **类名**：使用 `PascalCase`，如 `Character`, `BaseSkill`
- **函数/方法名**：使用 `snake_case`，如 `use_skill`, `take_damage`
- **常量**：使用 `UPPER_SNAKE_CASE`，如 `GAME_SIDE_COUNT`
- **私有成员**：使用单下划线前缀，如 `_GameSide`, `_add_character`
- **文件/模块名**：使用 `snake_case`，如 `character.py`, `_base.py`

#### 类型注解

- 所有函数和方法必须包含类型注解
- 使用 `typing` 模块的类型，如 `List`, `Dict`, `Optional`
- 避免使用 `Any`，除非必要

#### 文档字符串

- 所有公共类和方法必须包含文档字符串
- 使用 Google 风格的文档字符串格式
- 说明参数、返回值和可能的异常

#### 导入顺序

1. 标准库导入
2. 第三方库导入
3. 本地应用导入

每组导入之间用空行分隔。

### 架构规范

#### 事件驱动设计

- 所有游戏操作通过事件系统处理
- 事件放入队列，按顺序处理
- 事件可以被 Hook 拦截和修改

#### 状态管理

- 游戏状态集中在 `State` 类中管理
- 支持状态快照和恢复（用于预检查和回滚）
- 状态变更必须通过事件系统

#### 模块化设计

- 每个系统独立模块（角色、技能、事件、卡牌等）
- 模块间通过接口交互，避免直接依赖
- 使用依赖注入而非全局状态

#### 数据驱动

- 角色数据通过 YAML 配置文件定义
- 避免硬编码游戏数据
- 配置与代码分离

### 测试规范

#### 测试覆盖

- 核心功能必须有单元测试
- 关键路径必须有集成测试
- 测试覆盖率目标：80%+

#### 测试命名

- 测试函数名以 `test_` 开头
- 测试文件名以 `test_` 开头
- 测试类名以 `Test` 开头

#### 测试结构

- 使用 `pytest` 作为测试框架
- 使用 fixture 管理测试数据
- 测试应该独立，不依赖执行顺序

### 提交规范

#### Commit 消息

使用清晰的提交消息格式：

```
<type>: <subject>

<body>

<footer>
```

**Type**：
- `feat`: 新功能
- `fix`: 修复 bug
- `docs`: 文档更新
- `style`: 代码格式（不影响功能）
- `refactor`: 重构
- `test`: 测试相关
- `chore`: 构建/工具相关

**示例**：
```
feat: 实现元素反应系统

- 添加增幅反应（蒸发、融化）
- 添加剧变反应（超载、感电等）
- 实现反应伤害计算逻辑

Closes #123
```

### 开发流程

1. **功能开发**：
   - 从路线图选择任务
   - 创建功能分支
   - 实现功能并编写测试
   - 确保所有测试通过

2. **代码审查**：
   - 提交前检查代码规范
   - 运行 linter 和类型检查
   - 确保文档更新

3. **合并**：
   - 通过所有测试
   - 代码审查通过
   - 更新相关文档

### 依赖管理

- 使用 Poetry 管理依赖
- 新依赖需要说明理由
- 定期更新依赖版本
- 避免不必要的依赖

### 文档要求

- 新功能必须更新相关文档
- 重大变更需要更新架构文档
- API 变更需要更新 README
- 复杂逻辑需要代码注释

## 规则执行

- 所有代码必须通过 linter 检查
- 所有测试必须通过
- 不符合规范的代码不应合并到主分支
- 定期审查和更新规则

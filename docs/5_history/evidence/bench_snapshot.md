# 快照 / 恢复基准测试

来源：`tools/bench_snapshot.py`（已提交 `8000cd4`）

**待回答的问题**：基于 Python 驱动的 MCTS 在现有 ctypes 桥接层上是否可行？具体来说，快照和恢复操作是否足够快，能够在每次决策中执行数百次模拟？随着对局规模增大，开销是否能优雅地线性扩展？

## 结果（2026-04-14）

| 场景 | 步骤 µs | 快照 µs | 恢复 µs | 克隆 µs | 类 MCTS 模拟 µs | 游戏数/小时 @ 400×30 |
|---|---|---|---|---|---|---|
| 1v1 L1 | 45 | 8.2 | 7.4 | 8.9 | 926 | 324 |
| 1v1 L1+L2 | 58 | 8.0 | 7.5 | 8.9 | 1487 | 202 |
| 2v2 L1+L2 | 64 | 8.1 | 7.5 | 8.9 | 2264 | 133 |
| 3v3 L1+L2 | 88 | 8.2 | 7.5 | 9.1 | 2986 | 100 |

列说明：
- **步骤 µs**：包含 ctypes 边界的每步执行时间
- **快照 µs**：通过 `GameSnapshot` 捕获完整游戏状态的时间
- **恢复 µs**：通过 `GameRestore` 恢复状态的时间（同时推进快照的 RNG，使每次调用产生不同的随机模拟结果）
- **克隆 µs**：`GameClone`（完全独立的引擎句柄）的时间
- **类 MCTS 模拟 µs**：一次快照 + 约 30 步随机走子 + 一次恢复 + 一次 snapshot_free 的总时间
- **游戏数/小时**：按 400 次模拟/决策 × 30 次决策/局的单进程 Python 推算的吞吐量

## 关键发现

1. **快照和恢复的时间复杂度为 O(1)，与对局规模无关**。四种场景均显示约 8 µs，不受计数器数量、手牌数量或角色数量影响。这证实了 `Game.DeepCopy` 实现的扁平切片布局没有产生任何规模相关的额外开销。

2. **步骤开销随对局规模适度增长**（45 → 88 µs），主要驱动因素是计数器组写入和钩子分发次数，而非数据结构遍历开销。

3. **模拟开销由步骤执行主导**，而非快照处理。恢复 + 步骤 + snapshot_free 的额外开销占总模拟时间的比例 < 5%。

4. **单进程吞吐量**为 100–300 局/小时，乘以 4 个 CPU 核心，可达 10–28k 局/天，**远高于** PPO 模拟的约 1.6k 局/天。存在充足的并行扩展空间。

5. **每次模拟预算**：以 1 ms / 次模拟计，400 次模拟的决策耗时约 0.4 秒实际时间。一局 30 次决策的游戏耗时约 12 秒实际时间。1 小时训练每进程可产生约 300 局，4 个进程合计约 1200 局。

## 对设计的启示

- **MCTS 可行性**：已确认。推进 Python MCTS 方案。
- **并行扩展**：单进程对于 MVP 已足够；多进程（4-8 个工作进程）是有需要时的自然扩展方向。
- **无需将 MCTS 移植到 Go**：每步 ctypes 开销占步骤时间的比例可接受，而 Go MCTS 的工程成本远高于所节省的时间。
- **快照 API 保持现状**：无需进行性能优化。

## 重现基准测试

```bash
.venv/bin/python -m tools.bench_snapshot --scenario 1v1_L1
.venv/bin/python -m tools.bench_snapshot --scenario 1v1_L12
.venv/bin/python -m tools.bench_snapshot --scenario 2v2_L12
.venv/bin/python -m tools.bench_snapshot --scenario 3v3_L12
```

每次运行会打印步骤 / 快照 / 恢复 / 克隆 / 类 MCTS 模拟的耗时，以及按 400 次模拟/决策推算的游戏数/小时。
